# CRUD Integration

Create, Read, Update, Delete (CRUD) is the pattern established by traditional Phoenix code generators, including `phx.gen.auth`.
This guide documents the steps to integrate `WebauthnComponents` with an application where `phx.gen.auth` establishes the baseline authentication and session management mechanisms.
`WebauthnComponents` manages the client-server ceremonies for credential registration and authentication, and decisions about data storage are left to the host application.

The code examples in this guide may be modified to fit the naming conventions and particular requirements of your application.
They follow the reference implementation in [`liveshowy/webauthn_components_demo`](https://github.com/liveshowy/webauthn_components_demo), specifically [commit `73324c8`](https://github.com/liveshowy/webauthn_components_demo/commit/73324c8fc32d633def7a6b2addcfe3596f11ee50).
Examples use `MyApp` and `MyAppWeb`; substitute your own module names.

## Prerequisites

- Elixir 1.18 or later and Phoenix 1.8 or later.
- PostgreSQL (the migration below uses PostgreSQL's `:bytea` type).
- A secure browser context. `localhost` is treated as secure during development; production deployments require HTTPS.
- A basic understanding of the files generated by `mix phx.gen.auth`.

## Generate a new Phoenix application

Create the application with binary primary keys:

```shell
mix phx.new my_app --binary-id
cd my_app
```

`--binary-id` configures the generators to use `:binary_id` primary and foreign keys.
This guide assumes binary user IDs. If you use an existing application, make sure the `users` table and the credential foreign key use the same type.

## Generate authentication code

Generate the authentication LiveViews, schemas, and session management:

```shell
mix phx.gen.auth Accounts User users --binary-id --live
mix deps.get
mix ecto.setup
```

This establishes:

- User registration, login, logout, and password reset flows.
- Email confirmation and magic-link login.
- A `UserSessionController` for creating and deleting server-side sessions.
- A `Settings` LiveView with sudo-mode protection.
- `current_scope` assigns and `UserAuth` helpers.

The remaining steps add Passkeys alongside these existing mechanisms.

## Add `WebauthnComponents` as a dependency

Add the dependency to `mix.exs`:

```elixir
# my_app/mix.exs
defp deps do
  [
    # ...
    {:webauthn_components, "~> 0.11"}
  ]
end
```

Install it:

```shell
mix deps.get
```

`WebauthnComponents` depends on `Wax` for the server-side WebAuthn ceremonies and provides `WebauthnComponents.CoseKey` as an Ecto type for storing public keys.
No additional configuration is required for the examples in this guide.

## Add `WebauthnHooks` to `assets/js/app.js`

The package exports three LiveView hooks:

- `ClientCapabilitiesHook`
- `RegistrationHook`
- `AuthenticationHook`

Each component sets a matching `phx-hook` attribute, so the hooks must be registered globally with `LiveSocket`.
Import the hooks and merge them into the socket configuration:

```js
// assets/js/app.js
import {Socket} from "phoenix"
import {LiveSocket} from "phoenix_live_view"
import {hooks as colocatedHooks} from "phoenix-colocated/my_app"
import topbar from "../vendor/topbar"
import * as WebauthnHooks from "webauthn_components"

const csrfToken = document.querySelector("meta[name='csrf-token']").getAttribute("content")
const liveSocket = new LiveSocket("/live", Socket, {
  longPollFallbackMs: 2500,
  params: {_csrf_token: csrfToken},
  hooks: {...WebauthnHooks, ...colocatedHooks},
})
```

> **Bundler note**
>
> The hooks are defined in the dependency at `priv/static/webauthn_hooks.js`.
> If your bundler cannot resolve the package entry point, import that file directly instead:
>
> ```js
> import * as WebauthnHooks from "../../deps/webauthn_components/priv/static/webauthn_hooks.js"
> ```

## Add `PublicKeyCredential` schema and migration

Credentials are stored in their own table. The credential ID is generated by the authenticator, so the schema does not autogenerate a primary key.

Create the migration:

```elixir
# priv/repo/migrations/20261004203857_create_public_key_credentials.exs
defmodule MyApp.Repo.Migrations.CreatePublicKeyCredentials do
  use Ecto.Migration

  def change do
    create table(:public_key_credentials, primary_key: false) do
      add :id, :bytea, primary_key: true
      add :label, :string
      add :public_key, :binary
      add :user_id, references(:users, type: :binary_id, on_delete: :delete_all)

      timestamps(type: :utc_datetime)
    end

    create index(:public_key_credentials, [:user_id])
  end
end
```

> **Database note**
>
> `:bytea` is PostgreSQL-specific. For MySQL or SQLite, use the binary/blob type supported by your adapter. The important part is that the credential ID and public key are stored as binary data.

> **Migration name**
>
> Generate the migration in your own project with `mix ecto.gen.migration create_public_key_credentials` so the filename uses a unique timestamp.

Create the schema:

```elixir
# lib/my_app/accounts/public_key_credential.ex
defmodule MyApp.Accounts.PublicKeyCredential do
  use Ecto.Schema
  import Ecto.Changeset
  alias MyApp.Accounts.User

  @primary_key {:id, :binary, autogenerate: false}
  @foreign_key_type :binary_id
  schema "public_key_credentials" do
    field :label, :string, default: "Default"
    field :public_key, WebauthnComponents.CoseKey
    belongs_to :user, User

    timestamps(type: :utc_datetime)
  end

  @doc false
  def register_changeset(public_key_credential, attrs) do
    public_key_credential
    |> cast(attrs, [:id, :label, :public_key, :user_id])
    |> validate_required([:id, :label, :public_key, :user_id])
  end

  def label_changeset(public_key_credential, attrs) do
    public_key_credential
    |> cast(attrs, [:label])
    |> validate_required([:label])
  end
end
```

Key details:

- `@primary_key {:id, :binary, autogenerate: false}` because the credential ID comes from the authenticator.
- `WebauthnComponents.CoseKey` encodes and decodes the COSE public key as CBOR when reading and writing the database.
- `:label` is user-facing metadata and does not participate in the ceremony.
- `belongs_to :user` associates each credential with its owner.

Run the migration:

```shell
mix ecto.migrate
```

## Add functions to the `Accounts` context

Update the aliases and add the credential functions:

```elixir
# lib/my_app/accounts.ex
defmodule MyApp.Accounts do
  import Ecto.Query, warn: false
  alias MyApp.Repo

  alias MyApp.Accounts.{User, UserToken, UserNotifier, PublicKeyCredential}

  # ...

  def get_user!(id, preloads \\ []) do
    User
    |> Repo.get!(id)
    |> Repo.preload(preloads)
  end

  # ...

  def register_credential(attrs) do
    %PublicKeyCredential{}
    |> PublicKeyCredential.register_changeset(attrs)
    |> Repo.insert()
  end

  def get_credential(credential_id, preloads \\ []) do
    PublicKeyCredential
    |> Repo.get(credential_id)
    |> Repo.preload(preloads)
  end

  def rename_credential(public_key_credential, attrs) do
    public_key_credential
    |> PublicKeyCredential.label_changeset(attrs)
    |> Repo.update()
  end

  def delete_credential(public_key_credential) do
    Repo.delete(public_key_credential)
  end
end
```

- `get_user!/2` accepts preloads so the login flow can fetch a user and all of their credentials in one call.
- `register_credential/1` inserts the credential returned by the registration ceremony.
- `get_credential/2` looks up a credential by ID and optionally preloads the owner.
- `rename_credential/2` updates only the user-facing label.
- `delete_credential/1` removes a credential.

> **Ownership check**
>
> The reference implementation looks up credentials by ID only. In a production application, scope rename and delete operations to the signed-in user as well, for example with `Repo.get_by(PublicKeyCredential, id: credential_id, user_id: user.id)`.

`@capabilities` starts as an empty map and is populated by `ClientCapabilitiesComponent`.

Update `mount/3` to build the registration options and preload the user's credentials:

```elixir
@impl true
def mount(_params, _session, socket) do
  user = socket.assigns.current_scope.user
  email_changeset = Accounts.change_user_email(user, %{}, validate_unique: false)
  password_changeset = Accounts.change_user_password(user, %{}, hash_password: false)

  public_key_options = %WebauthnComponents.PublicKeyCredentialCreationOptions{
    user: %WebauthnComponents.User{
      id: user.id,
      name: user.email,
      display_name: user.email
    },
    rp: %WebauthnComponents.RelyingParty{
      id: socket.endpoint.host(),
      name: "My App"
    }
  }

  socket =
    socket
    |> update(
      :current_scope,
      &Map.update!(&1, :user, fn user -> Repo.preload(user, [:public_key_credentials]) end)
    )
    |> assign(:current_email, user.email)
    |> assign(:email_form, to_form(email_changeset))
    |> assign(:password_form, to_form(password_changeset))
    |> assign(:trigger_submit, false)
    |> assign(:capabilities, %{})
    |> assign(:public_key_options, public_key_options)

  {:ok, socket}
end
```

The WebAuthn `user.id` should be a stable identifier. Using the database ID is a good choice: unlike an email address, it never changes, and the authenticator stores it as the credential's `userHandle`.
The relying party ID must be the effective domain of the site, without a scheme or port.
For local development, `socket.endpoint.host()` returns `localhost`.

Add the message handlers:

```elixir
@impl true
def handle_info({:client_capabilities, capabilities}, socket) do
  {:noreply, assign(socket, :capabilities, capabilities)}
end

def handle_info({:error, webauthn_error}, socket) do
  Logger.error(webauthn_error)
  {:noreply, socket}
end

def handle_info(%Wax.AuthenticatorData{} = authenticator_data, socket) do
  %Wax.AuthenticatorData{
    attested_credential_data: %Wax.AttestedCredentialData{
      credential_id: credential_id,
      credential_public_key: credential_public_key
    }
  } = authenticator_data

  attrs = %{
    "id" => credential_id,
    "public_key" => credential_public_key,
    "user_id" => socket.assigns.current_scope.user.id
  }

  case Accounts.register_credential(attrs) do
    {:ok, _credential} ->
      {
        :noreply,
        socket
        |> push_navigate(to: ~p"/users/settings")
      }

    {:error, error} ->
      Logger.error(error)

      {
        :noreply,
        socket
        |> put_flash(:error, "Failed to register credential: #{inspect(error)}")
      }
  end
end
```

When the registration ceremony succeeds, `RegistrationComponent` sends a `%Wax.AuthenticatorData{}` struct to the parent LiveView.
The attested credential data contains everything required for future authentication:

- `:credential_id` becomes the primary key.
- `:credential_public_key` is stored with the `CoseKey` Ecto type.
- `:user_id` associates the credential with the signed-in user.

The reference implementation navigates back to the settings page after registration, rename, and delete so the preloaded credential list is refreshed.
For a smoother experience, you can update the current scope in place instead.

Add the event handlers for renaming and deleting credentials:

```elixir
def handle_event("update-credential-label", params, socket) do
  %{"credential_id" => credential_id, "label" => label} = params

  with {:ok, credential_id} <- Base.decode64(credential_id),
       %PublicKeyCredential{} = credential <- Accounts.get_credential(credential_id),
       {:ok, _} <- Accounts.rename_credential(credential, %{"label" => label}) do
    {
      :noreply,
      socket
      |> push_navigate(to: ~p"/users/settings")
      |> put_flash(:info, "Credential label updated successfully.")
    }
  else
    error ->
      Logger.error(error)
      {:noreply, socket |> put_flash(:error, "Failed to update credential label.")}
  end
end

def handle_event("delete-credential", params, socket) do
  %{"credential_id" => credential_id} = params

  with {:ok, credential_id} <- Base.decode64(credential_id),
       %PublicKeyCredential{} = credential <- Accounts.get_credential(credential_id),
       {:ok, _} <- Accounts.delete_credential(credential) do
    {
      :noreply,
      socket
      |> push_navigate(to: ~p"/users/settings")
      |> put_flash(:info, "Credential deleted successfully.")
    }
  else
    error ->
      Logger.error(error)
      {:noreply, socket |> put_flash(:error, "Failed to delete credential.")}
  end
end
```

> **Error handling**
>
> The `RegistrationComponent` can also send a `Wax` error struct directly when server-side verification fails, such as `%Wax.InvalidCBORError{}` or `%Wax.ExpiredChallengeError{}`.
> Add `handle_info/2` clauses for the errors you expect, or a catch-all clause that logs the error and shows a flash message.
>
> `ClientCapabilitiesComponent` sends `{:invalid_event, event, payload}` when `PublicKeyCredential.getClientCapabilities()` is unavailable. Handle that message in LiveViews that render the component.

Add the message handlers:

```elixir
@impl true
def handle_info({:client_capabilities, capabilities}, socket) do
  # Trigger autofill UI
  # See https://web.dev/articles/passkey-form-autofill for details
  if capabilities["conditionalGet"] do
    send_update(WebauthnComponents.AuthenticationComponent,
      id: "passkey-authentication-component",
      mediation: "conditional"
    )
  end

  {:noreply, socket}
end

def handle_info(%FindUser{user_handle: user_id}, socket) do
  %User{public_key_credentials: public_key_credentials} =
    Accounts.get_user!(user_id, [:public_key_credentials])

  send_update(WebauthnComponents.AuthenticationComponent,
    id: "passkey-authentication-component",
    credentials: public_key_credentials
  )

  {:noreply, socket}
end

def handle_info({credential_id, %Wax.AuthenticatorData{sign_count: 0}}, socket) do
  # NOTE: This example simply accepts authenticator data with a sign count of 0 to start a user session.
  # Consider checking other fields based on your security requirements.
  # See https://www.w3.org/TR/webauthn-1/#verifying-assertion for suggested verification steps.
  credential_form =
    to_form(%{"credential_id" => Base.url_encode64(credential_id)}, as: "credential")

  {
    :noreply,
    socket
    |> assign(:trigger_credential_submit, true)
    |> assign(:credential_form, credential_form)
  }
end

def handle_info(%Wax.InvalidClientDataError{} = error, socket) do
  Logger.warning(error)

  {
    :noreply,
    socket
    |> put_flash(:error, "Unable to sign in")
  }
end

def handle_info({:error, payload}, socket) do
  Logger.warning(payload)

  {
    :noreply,
    socket
  }
end
```

The flow is:

1. `ClientCapabilitiesComponent` reports browser support. If `conditionalGet` is available, the authentication component switches to conditional mediation and the browser can offer a Passkey while the user interacts with the page.
2. The user selects a Passkey. `AuthenticationComponent` sends `%FindUser{user_handle: user_id}` to the LiveView.
3. The LiveView looks up the user by the stable `userHandle` (the user's database ID) and sends the user's credentials back with `send_update/3`.
4. `AuthenticationComponent` verifies the assertion against the stored public key and sends `{credential_id, %Wax.AuthenticatorData{}}` on success.
5. The LiveView places the credential ID in the hidden form and triggers a native submit. `UserSessionController` creates the session.

> **Sign count**
>
> The example accepts only authenticator data with `sign_count: 0`, which simplifies the demonstration.
> A production application should verify the signature counter according to its security requirements and decide how to handle a counter that does not increase.

## Update `UserSessionController`

Add the aliases and the Passkey login clause:

```elixir
# lib/my_app_web/controllers/user_session_controller.ex
defmodule MyAppWeb.UserSessionController do
  use MyAppWeb, :controller

  alias MyApp.Accounts
  alias MyApp.Accounts.PublicKeyCredential
  alias MyApp.Accounts.User
  alias MyAppWeb.UserAuth

  # ...

  # passkey login
  defp create(conn, %{"credential" => credential_params}, info) do
    %{"credential_id" => credential_id} = credential_params
    credential_id = Base.url_decode64!(credential_id)

    case Accounts.get_credential(credential_id, [:user]) do
      %PublicKeyCredential{user: %User{} = user} ->
        conn
        |> put_flash(:info, info)
        |> UserAuth.log_in_user(user, credential_params)

      _ ->
        conn
        |> put_flash(:error, "Invalid credential")
        |> redirect(to: ~p"/users/log-in")
    end
  end

  # ...
end
```

The generated controller has two public `create/2` clauses which delegate to a private `create/3` with an informational message.
Add the new private clause alongside the existing magic-link and email/password clauses.
The `%{"credential" => ...}` pattern distinguishes Passkey submissions from the other login methods.

This clause:

1. URL-decodes the credential ID from the hidden form.
2. Looks up the credential and preloads its owner.
3. Starts a normal server-backed session with `UserAuth.log_in_user/3`, reusing the generated session and remember-me behavior.
4. Redirects back to the login page with an error if the credential is not found.

> **Security warning: bind the hand-off to a verified assertion**
>
> The reference flow verifies the WebAuthn assertion inside `AuthenticationComponent`, then posts only the credential ID to the controller.
> Because credential IDs are public identifiers, the controller cannot tell whether a POST came from that verified LiveView or from an attacker who knows a credential ID.
> In a production application, do not create a session from the ID alone.
>
> After a successful verification, sign a short-lived token containing the credential ID, or store a one-time nonce in the session, and verify it in the controller before calling `UserAuth.log_in_user/3`. For example:
>
> ```elixir
> # In the Login LiveView, after AuthenticationComponent reports success:
> token = Phoenix.Token.sign(socket.endpoint, "passkey-login", credential_id)
> credential_form = to_form(%{"token" => token}, as: "credential")
> ```
>
> ```elixir
> # In UserSessionController
> defp create(conn, %{"credential" => %{"token" => token}}, info) do
>   with {:ok, credential_id} <-
>          Phoenix.Token.verify(conn, "passkey-login", token, max_age: 60),
>        %PublicKeyCredential{user: %User{} = user} <-
>          Accounts.get_credential(credential_id, [:user]) do
>     conn
>     |> put_flash(:info, info)
>     |> UserAuth.log_in_user(user)
>   else
>     _ ->
>       conn
>       |> put_flash(:error, "Invalid credential")
>       |> redirect(to: ~p"/users/log-in")
>   end
> end
> ```
>
> A one-time nonce stored in the session is stronger than a reusable token, because it cannot be replayed within the token's lifetime.

## Security Considerations

The reference implementation focuses on demonstrating the CRUD integration. Review these points before deploying to production:

- **Do not trust a credential ID as proof of authentication.** Verify a signed token or one-time nonce in the controller, as described in the [`UserSessionController`](#update-usersessioncontroller) section.
- **Scope credential mutations to the current user.** Rename and delete lookups should include `user_id: current_scope.user.id`.
- **Handle invalid input.** `Base.url_decode64!/1` raises on malformed input. Use `Base.url_decode64/2` and handle the error tuple.
- **Handle unknown user handles.** `Accounts.get_user!/2` raises when no user matches. Use a lookup that returns a result tuple and reject unknown credentials instead of crashing the LiveView.
- **Handle all ceremony errors.** Add clauses for Wax errors sent by the components, not just client-side `{:error, payload}` messages.
- **Verify the signature counter.** The login example only matches `sign_count: 0`. Decide how to persist and compare counters to detect cloned authenticators.
- **Require user verification when appropriate.** Creation defaults to `user_verification: :required`; request options default to `:preferred`. Set `:required` if your threat model calls for it.
- **Use a stable user handle.** The examples use `user.id`. Do not use an email address or another mutable value as the WebAuthn user ID.
- **Use HTTPS in production.** WebAuthn requires a secure context. The relying party ID must match the site's effective domain.
- **Configure the endpoint URL.** The components use `socket.endpoint.url()` as the expected origin during verification. Make sure the endpoint URL matches the browser origin in each environment.
- **Prevent duplicate registrations.** Populate `:exclude_credentials` from the user's existing credentials if you want the authenticator to reject re-registration of the same device.
- **Keep session management centralized.** The Passkey flow reuses `UserAuth.log_in_user/3`, so session renewal, remember-me cookies, and token disconnection continue to work as generated by `phx.gen.auth`.
